# SalesVisor v2: контроль исполнения заказов

Черновик от 29.09.2026. Составлен по реальным выгрузкам (отчёт по отрезкам за 21.09 и 29.09, светофор v2) и по устройству пилота VOLS-Zakazy 2.0. Код пилота за основу не берём, берём только то, что он уже выяснил о данных.

## 1. Что показали выгрузки

**Отчёт по отрезкам** — главный источник. Одна строка соответствует одному отрезку позиции заказа, всего 67,8 тыс. строк и 84 колонки. Ключ строки: заказ клиента, позиция и номер отрезка.

| Что нужно | Колонка в отчёте |
|---|---|
| Текущая обещанная дата | Треб. дата поставки (одна на позицию) |
| План отгрузки | План дата отгрузки (фактуры) |
| Факт отгрузки | Факт. дата поставки |
| Передача в производство | Дата передачи в производство |
| Этап отрезка | Статусы Произведен → На складе → Готов к отгрузке → Отгружен → Отфактурирован, плюс В пути. Значение @08@ означает «да», @EB@ означает «нет» |
| Менеджер | Создал (логин SAP) |
| Приёмка заказа | Причина отклонения: Z4 Готов к производству, Z6 Прогноз/аванс, Z7 Бизнес-план |
| Связь с Битрикс24 | Номер задачи в Битрикс. Заполнен в 9,3 тыс. строк свободным текстом, например «Задача № 313360 Губанов» или «304730» |
| Деньги | Нетто план/факт, МЗ, МП |

В выгрузке за 29.09 не отгружено 9,4 тыс. отрезков по 637 заказам. Это рабочий объём, который нужно контролировать.

**Светофор v2** считает смещение по позиции: первая декада (на момент перевода в Z4) против текущей. Цвета: зелёный — смещение 0 и меньше, жёлтый — 10–30 дней, красный — больше 30 дней.

**Первая требуемая дата берётся из светофора.** «Первая декада» и есть первая требуемая дата клиента. Даты у вас назначаются по декадам: план отгрузки всегда 10-го, 20-го или последнего числа месяца, поэтому точности до декады достаточно. «Текущая декада» показывает, что с позицией сейчас. В 91% позиций она совпадает с декадой «ПланДатаОтгрузки».

Поэтому v2 берёт первую дату прямо из светофора и не восстанавливает её по снимкам. Снимки отчёта по отрезкам всё равно сохраняем: они дают журнал переносов (когда и на сколько сдвинулась позиция) и подстраховывают позиции, которых нет в светофоре.

## 2. Как устроена v2

```
SAP / Metabase ──(выгрузки по расписанию)──► Загрузчик ──► PostgreSQL ◄── Веб-интерфейс (менеджеры, сервис)
                                                           ▲   │
                              Битрикс24 ──(исходящий вебхук)─┘   └─(входящий вебхук)──► Битрикс24
```

- **Загрузчик.** Раз в день, а лучше несколько раз, забирает отчёт по отрезкам: из общей папки, по API Metabase или прямым запросом к витрине. Каждую загрузку он сохраняет как снимок. Затем сравнивает снимок с прошлым и пишет изменения в журнал: перенос даты, смену статуса, новые отрезки.
- **База.** PostgreSQL: объём снимков растёт на ~70 тыс. строк в день, SQLite для этого мал. Основные таблицы:
  - `positions`: первая и текущая обещанная дата, дата каждой из них, число переносов, план, этап, менеджер, клиент;
  - `segments`: отрезки и их статусы;
  - `snapshots`: загруженные снимки;
  - `change_log`: журнал изменений;
  - `plan`: план производства — линия, окончание плана, партия;
  - `comments`: комментарии;
  - `bitrix_links`: связь заказа с задачей и сделкой в Битрикс24.
- **Правила статуса.** Считаются по позиции и по заказу в целом:
  - смещение от первой даты в днях и в декадах, с цветами как у светофора;
  - просрочка: треб. дата прошла, а позиция не отгружена;
  - риск: план отгрузки позже треб. даты или в плане производства позиции нет;
  - готовность: сколько отрезков прошло каждый этап.
- **Интерфейс.**
  - Менеджер видит свои заказы, вход через учётку домена или Битрикс24. Сверху красные и жёлтые позиции, в карточке история дат, этапы отрезков и ссылка на задачу в Битрикс24.
  - Сервис видит всё и может фильтровать по отделу, клиенту, декаде и цвету.
  - Руководитель видит сводку по отделам: сколько позиций сдвинуто, на сколько и по каким причинам.

## 3. Связь SAP и Битрикс24

Уточнено 29.09: Битрикс24 коробочный, вебхуки есть, номера заказов SAP в Битрикс24 сейчас не записываются.

Сейчас их связывает только поле «Номер задачи в Битрикс» в SAP: 1 374 заказа из 6 339, свободный текст. Предлагаю связь в три шага.

**Шаг 1. Карточка связи в SalesVisor, работает сразу.** Приложение уже достаёт номер задачи из текста (87% случаев). Для остальных менеджер указывает номер задачи или сделки в карточке заказа (сделано). Ручная привязка важнее номера из SAP, а плитка «Без связи с Битрикс24» показывает, где связи ещё нет. Если вебхук настроен, в карточке видны название, статус, ответственный и срок задачи. Так таблица «заказ SAP ↔ задача/сделка Битрикс24» появляется без доработок SAP и Битрикс24.

**Шаг 2. Номер заказа SAP в Битрикс24.** В сделке заводим пользовательское поле «Заказ SAP» (UF_CRM_SAP_ORDER; может быть несколько номеров). SalesVisor заполняет его сам через входящий вебхук (`crm.deal.update`) по таблице связи из шага 1. После этого в Битрикс24 можно искать сделку по номеру заказа и строить отчёты. Здесь же можно вывести статус исполнения: цвет светофора, текущую декаду и готовность по отрезкам.

**Шаг 3. Номер сделки в SAP.** Отдельное поле в заказе клиента SAP вместо свободного текста. Это доработка на стороне SAP, её делает ваша команда SAP. Когда поле появится в отчёте по отрезкам, связь станет полностью автоматической.

**Что шлём в Битрикс24.** Всё через входящий вебхук; коробка в вашей сети, поэтому внешний доступ не нужен.
- Комментарий в задачу или сделку при переносе текущей декады. Уже реализовано и включается настройкой `BITRIX_POST_COMMENTS=1`.
- Уведомление менеджеру (`im.notify.system.add`), когда позиция стала жёлтой или красной или подходит срок без отгрузки.

Лимит Битрикс24 — около 2 запросов в секунду. Поэтому запросы собираем пачками через `batch` и шлём только изменения.

**Что получаем из Битрикс24.** Исходящий вебхук на события `ONCRMDEALUPDATE` и `ONTASKCOMMENTADD`: договорённости с клиентом попадают в историю заказа.

**Кто есть кто.** Менеджер в SAP — логин из поля «Создал», например EGILIASHEVA. Для уведомлений нужна таблица соответствия логина SAP и пользователя Битрикс24. Её можно собрать по e-mail через `user.get`.

**Безопасность.** Адрес вебхука содержит ключ доступа, поэтому хранится только в `.env` на сервере. Для приложения нужен отдельный вебхук с правами на CRM, задачи, уведомления и пользователей.

## 4. Место в контуре «Инкаб ИИ»

Уточнено 29.09 по описанию контура (редакция 29.09.2026).

**Где работает.** Узел ai-ag (172.16.50.30), рядом с тендер-агентом: там есть ресурсы (8 ядер, 32 ГБ), выход в IPv4 к Битрикс24 `team.incab.ru` и SFTP-приёмник завода. Порт 8102, слушает только приватный адрес. Контейнеры `salesvisor:local` (веб и синхронизация) и Postgres, часовой пояс Asia/Yekaterinburg.

**Как сотрудник открывает.** Тем же способом, что и тендер-агент. Портал отдаёт раздел `/orders/` и проксирует запросы на ai-ag:8102. К каждому запросу портал добавляет общий секрет `X-SalesVisor-Token`, алиас `X-SalesVisor-User` и ФИО `X-SalesVisor-Person` (percent-encoding). SalesVisor без секрета отвечает 401, своих паролей не заводит. Доступ даёт список алиасов в портале, по образцу `INKAB_TENDER_USERS`. Адрес `/orders` без косой черты портал перенаправляет на `/orders/`, потому что страница обращается к API по относительным путям. `/api/health` открыт для монитора контура.

**Откуда берутся данные.** Metabase `metabase.incab.ru` виден только из сети Инкаба, а серверы контура арендованы в Timeweb. Поэтому два пути:
- основной: завод кладёт две выгрузки (вопросы 522 и 573) в SFTP `zavod-sftp` → `/data/SAP/salesvisor` по расписанию. SalesVisor каждый час забирает новые файлы, сам различает отчёт и светофор, загружает сначала отрезки, потом светофор. Разобранные файлы уходят в `done/`, неразобранные в `failed/`. Нужны публичный ssh-ключ завода и задание на стороне завода, которое выгружает CSV из Metabase;
- если ИТ откроет Metabase для ai-ag, достаточно `METABASE_API_KEY` в `.env`, папка не понадобится.

**Битрикс24.** Вызовы идут с ai-ag по IPv4. Нужен отдельный служебный вебхук (CRM, задачи, уведомления, пользователи), не личный: вебхук действует от имени владельца.

**Выкладка.** GitHub с серверов недоступен, Docker Hub отвечает 429. Код переносится с ноутбука РП, образ собирается поверх уже загруженного `python:3.12-slim`, базовые образы при необходимости переносятся через `docker save/load`. Версии попадают в `ai-kb:/srv/git` общим часовым снимком.

**Модели.** SalesVisor языковые модели не использует. Если понадобится разбор или сводка, вызовы идут только через шлюз ключом `svc-salesvisor` и только на модели Сбера: в данных есть заказчики и суммы.

## 5. Порядок работ

1. Загрузчик светофора (первая и текущая декада, смещение, цвет) и отчёта по отрезкам (этапы, снимки, журнал переносов). Проверка на выгрузках за 21.09 и 29.09.
2. Экран позиций и заказов со светофором, карточка заказа, роли менеджер и сервис.
3. План производства и выпуск (форматы как в пилоте: план, выпуск, диспетчерский отчёт).
4. Битрикс24: чтение задач, комментарии о переносах, уведомления менеджерам.
5. Развёртывание на ai-ag: Docker, вход через портал, приём выгрузок по SFTP (приложение готово, ждёт ключа завода и раздела в портале).
